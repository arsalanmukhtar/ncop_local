Why NCOP Exists #

Pakistan sits in the middle of one of the world’s most disaster-exposed geographies. Monsoon floods on the Indus. Glacial-lake outburst floods in the Karakoram. Heatwaves in Sindh. Cyclones on the Arabian coast. Wildfires in KP. Earthquakes across the northern belt. Locust swarms coming in from the west. Between them, dozens of institutions publish authoritative data every single day — and until NCOP, an emergency operator responding to a real incident had to open eight browser tabs just to see what was happening.

The core problem: the data existed. The picture didn’t. Weather, floods, air quality, seismic activity, food security, live station feeds, satellite imagery — each source lived on its own website, in its own format, on its own refresh cadence, behind its own login. Analysts spent hours collecting before they could start deciding.

NCOP was commissioned by Pakistan’s National Disaster Management Authority (NDMA) to solve that specific problem. Not a new dataset. Not a new model. A single operational picture where every meaningful feed — PMD, FFD, NWFC, ECMWF, GDACS, EONET, USGS, IPC, PBS, WAQI, GloFAS, GeoServer, IMERG, DWD, Meteoblue, Copernicus, GEE — is fused onto one Mapbox canvas, live, cached, colour-coded, playable through a shared temporal slider, and comparable side-by-side.

The value isn’t any one layer. The value is seeing them at the same time: an IPC food-insecurity polygon over a GloFAS discharge forecast over an NWFC weather warning over a live PMD station reading, all keyed to the same district, all fetched by the same session. That’s the difference between reacting to a briefing 6 hours late and deploying assets 6 hours early.

What NCOP Is (in plain terms) #

Think of NCOP as Google Maps for emergencies. Same familiar map, same pan/zoom, same clean UI. The difference is what you can turn on on top of it.

The three things a user does

  1. Pick layers from the left-hand sidebar — an accordion of ~7 categories (GIS layers, weather, floods, air quality, agriculture, ocean, early warning). Each accordion contains subcategories, each subcategory contains toggles.
  2. Play time on the bottom timeline — for weather / satellite / forecast layers, hitting the play button animates a forecast frame-by-frame. Drag the slider to jump to any hour.
  3. Read what’s on the map — click any polygon or point for a popup card with the underlying data (station reading, forecast value, phase classification, upstream ID). For richer layers (heatwave, IPC food security, crops, weather) there’s a follow-up modal with charts and tabs.

Where the data comes from (grassroots view)

NCOP itself doesn’t generate the data. Every layer is fetched from an authoritative source — the same organisation that a paper briefing would quote — but instead of a PDF twelve hours later, you see the polygon on a map right now:

How to Use NCOP #

Everything the operator does on NCOP happens in one of four regions of the screen. Learn these and you know the whole UI.

1 · Turning layers on and off

  1. Click the hamburger menu (top-left corner). The sidebar slides in with every category available.
  2. Expand an accordion — GIS Layers, Weather Systems, Flood Monitoring, Air Quality, Agriculture Monitoring, Ocean & Coastal, or Early Warning.
  3. Expand a subcategory inside it (e.g. Weather Systems → PMD Predictions).
  4. Toggle a layer — either a switch (for “always-on” layers like boundaries) or a click-tile (for “time-aware” layers where the bottom slider lights up).
  5. Search — if you know the layer name, type it in the sidebar’s search box to filter every category instantly.

2 · Reading a temporal (time-aware) layer

  1. Click a temporal item (has a small clock/movie icon in the sidebar). The bottom slider appears with playable frames.
  2. Hit Play (left icon) to animate through the forecast hour-by-hour, or drag the slider handle to jump to a specific time.
  3. Change speed with the 1× pill — cycles through 0.5× / 1× / 2× / 4×.
  4. Read the legend — centre-bottom shows a colour ramp with values (mm, °C, %) so you know what the colours mean.
  5. Live timestep — the layer’s title area shows exactly which forecast hour is currently visible; it updates as you scrub.
  6. Adjust opacity with the blend button on the far right — useful when you want to see the basemap through a cloud-cover layer.
  7. Remove the layer with the trash icon; it doesn’t affect any other layer.

3 · Clicking a feature for details

  1. Click any polygon or point on the map. A popup opens with the feature’s underlying values (station reading, phase classification, forecast, area, etc.).
  2. Some popups launch a follow-up modal — e.g. IPC polygons expose an “Open Food Security Panel” button for a 4-tab draggable modal with charts, historical trends, and per-area breakdowns.
  3. Crop layers have an “Open Crop Explorer” button for a 6-tab modal spanning 44 years of national and district crop statistics.
  4. Close a popup by pressing ESC (there’s no close button on purpose — less chrome, cleaner map).

  1. Click the Split Compare icon (two-column icon on the right rail). The map splits vertically into Map A (left) and Map B (right).

Introduction #

NCOP is a real-time, multi-source geospatial dashboard built for Pakistan’s National Disaster Management Authority (NDMA) and the National Emergency Operations Centre (NEOC). It consolidates meteorological, hydrological, air-quality, oceanic and disaster-event data from domestic and international providers into a single, professionally-themed Mapbox-based web map — enabling planners, operators and decision-makers to assess hazard exposure and operating posture from one screen.

System Architecture #

NCOP follows a thin-server, smart-client model. The browser does all map rendering; Django serves the dashboard shell and acts as an authenticated reverse proxy / cache for upstream APIs.

Boundary serving

Administrative boundaries (national, provincial, district, tehsil) and infrastructure layers are served directly to the browser as Mapbox Vector Tiles from GeoServer’s GeoWebCache via TMS. Django is not in the hot path for boundary tiles — this keeps tile latency low and removes a hop.

Live data flow

Live point/polygon datasets (PMD stations, GDACS, EONET, USGS) flow as GeoJSON through Django proxies. Django provides three things on top of the upstream: schema normalisation, caching and SSL/Auth tunnelling.

Data Flow #

User toggles a layer

  1. Sidebar menu fires a change event → SourceLayerControl.addLayerByKey(key).
  2. Control looks up the ncop_menu_items config in map-layers.js.
  3. If the source isn’t already on the map, addMapboxSource(config.source) creates it.
  4. Each layer in config.layers is added via _addLayerAtCorrectOrder(), which respects the z-order rule (vector layers always above temporal rasters).
  5. The wrapper installed by LayerStyleConfig replays any persisted user overrides for that key.
  6. Active layer is registered in SourceLayerControl.activeLayers for later restore.

User switches the basemap

  1. map.setStyle(...) tears down every layer and source.
  2. Mapbox fires style.load on the map.
  3. SourceLayerControl.handleStyleLoad() iterates the saved order and re-calls addLayerByKey for each.
  4. For each re-add, LayerStyleConfig.#reapplyOverridesFor(key) reinstates the user’s saved paint/layout values.
  5. Temporal layers, label layers, and popup handlers all rebind via their own style.load listeners.

User drags the temporal slider

  1. Slider input event → setCurrentStep(index).
  2. The active temporal config is consulted to resolve the frame for that step.
  3. Old frame layers are removed; new frame layers are added at the correct z-order (below all vector layers).
  4. If the weather report panel is open, WeatherReportControl.#scheduleRender() debounces a fresh per-district sampling pass.

Layers & APIs Explained #

NCOP’s layers all reach the browser through the same pipeline, no matter which upstream serves them. Understanding that pipeline is the fastest way for a new developer or a client to reason about “where does this data come from and why is it fast enough.”

The five layer archetypes

Every layer in NCOP falls into one of five shapes. Once you recognise the shape, everything else about it — how it’s stored, how it’s rendered, how it’s cached — is predictable.

ShapeWhat it isHow it’s servedExample
Vector Tile Always-on polygon / line / point layer with fixed styling. Fast, zooms cleanly, tiled by Mapbox. GeoServer TMS tiles ({z}/{x}/{y}.pbf) hit directly from the browser. National Boundary, Rivers, Fault Lines, Flood Extents.
GeoJSON A single JSON feature-collection with dynamic per-feature styling. Best for “live” feeds where colour depends on an attribute. Django proxy fetches upstream, joins polygons + values, returns one JSON object. IPC food security, Crop Production choropleths, PMD Warnings.
Raster Tile Time-aware raster served as WMS tiles, one URL template per forecast timestep. External WMS server (DWD, ECMWF, Meteoblue) hit directly with a time= param per frame. DWD Satellite IR, IMERG Precipitation, ECMWF Temperature.
Image Frame Time-aware raster where each forecast hour is a single pre-rendered PNG pinned to 4 corner coordinates. Django proxy fetches the raw GeoTIFF from an authenticated source, warps + colorizes via GDAL, caches PNG on disk. PMD Predictions (WRFPRS / GDFS): precipitation, temperature, cloud cover, humidity.
Feature Popup Layer A base vector layer whose value is the click handler. Clicking a feature opens a card / modal with attributes + charts. Any of the above + a per-layer popup builder in layer-attribute-popup.js. Heatwave stations, IPC polygons, Crop districts, GLOF observations.

6 · UpstreamPMD Monitor: latest run, then per-frame .tif.
→
7 · GDALWarp EPSG:4326 → 3857, color-relief PNG.
→
8 · Disk cachePNG + JSON metadata under MEDIA_ROOT.
→
9 · JSON return{steps: [{date, url, coords}]} → browser.
→
10 · SliderupdateTempSliderAsync registers image sources; play.

Every layer follows the same shape. Steps 5-8 are optional (only for authenticated / colorized layers); everything else is universal. This uniformity is why adding a new layer typically takes only a registry entry + a loader function.

Why the browser never sees an upstream URL

NCOP’s browser bundle contains no upstream credentials, no upstream hostnames, no API keys for restricted sources. Every request that needs authentication or IP-restricted access goes through Django. This is intentional: it protects rotating credentials, it lets us cache aggressively at the server, and it gives us a single audit point when a source’s API shape changes.

The browser only knows about window.location.origin. Django translates /api/pmd/monitor/*, /api/ipc/*, /api/crops/*, etc. into the right upstream call, injects the right auth, and returns a normalised JSON shape the frontend already understands.

Cache layers — why NCOP feels instant

Three levels of cache stack on top of each other. Any one is enough to make a repeat visit fast; together they mean the same layer, opened twice in one session, costs zero network trips.

🌐 Browser cache
Standard HTTP cache on the returned PNGs / JSON
🖥️ Frontend memo
Loader factories (e.g. _PMD_PRED_CACHE Map) keep resolved frame arrays
🐍 Django in-memory cache

💾 On-disk cache

Cache invalidation is time-based, not manual. New model runs supersede old ones automatically because the “latest-run” lookup expires every 30 minutes; new frames get their own filenames so they can’t collide with older ones.

Temporal Layers #

Temporal layers are animated slider-driven layer sequences. Each entry in a temporal block defines an image preview, a theme (slider), and a title for the slider chrome. The slider expands the layer into N time-stepped frames at runtime; each frame consists of one or more vector or raster Mapbox layers with matching source-layer hooks.

Slider behaviour and rendering live in temporal-controls.js. The control:

  • Exposes window.getCurrentTemporalState() — { layerKey, currentEntry, currentIndex, date } — consumed by the Weather Report.
  • Re-binds on style.load so basemap switches don’t lose the active frame.
  • Respects the z-order rule: temporal layers are always added below any normal vector layer so popups land on the user-toggleable layer rather than the temporal raster.

NWFC Weather Icons (HTML markers) #

The NWFC Station Observations layer renders each feature as an HTML mapboxgl.Marker — same architecture GCOP’s own live NCOP uses. Each marker is a plain <div> containing an <img> for the weather icon (browser handles GIF animation natively) plus a <div> temperature label below it. No JavaScript animation loop, no StyleImageInterface dance.

Why HTML markers? Every attempt at a data-driven Mapbox symbol layer for this data silently fell through to the fallback sprite. Mapbox v3’s GeoJSON tile encoder was dropping properties added by mutating features after fetch — querySourceFeatures and queryRenderedFeatures both still showed the properties, but the tile-encoded form that layer ["get", …] expressions read from did not. Rather than fight the tile encoder, we bypass it: JS dispatcher picks the icon, HTML marker renders it directly.

  • Marker module: frontend/src/modules/nwfc-html-markers.js — NwfcHtmlMarkerManager listens for sourcedata / style.load on the nwfc_observations-source, reconciles markers per feature, tears them down on layer toggle-off and basemap swap.
  • Icon assets: 13 GIF/PNG files in frontend/src/assets/images/nwfc_icons/ — one per bucket. URLs surfaced via NWFC_WEATHER_ICON_URLS in nwfc-weather-icons.js.
  • 14 buckets — 13 with a real asset (thunderstorm, rain, drizzle, snow, fog, dust, overcast, cloudy, partly_cloudy, clear, windy, hot, cold) plus a Default thermometer 🌡 emoji for anything unrecognised (empty string, Smoke, N/A, etc.).
  • Icon dispatcher: nwfcWeatherBucket(text) in map-icons.js — case-insensitive substring match with a defined precedence: thunder / lightning → drizzle → shower / rain → snow / blizzard / sleet / hail → fog / mist / haze → dust / sandstorm → partly cloud → overcast → METAR codes (ovc, bkn, sct, few, skc, clr, nsc, ncd) → cloud → gust / wind → hot / scorch → cold / freez / chill → clear / sunny / fair → default.
  • METAR support: PMD’s NWFC scrape often returns aviation cloud-cover codes like SCT at 4000 feet, BKN at 3500 feet, OVC at 3000 feet. These are resolved before the generic cloud fallback: SCT/FEW → partly_cloudy, BKN → cloudy, OVC → overcast, SKC/CLR/NSC/NCD → clear.
  • Fixed 36 CSS-pixel size at every zoom, matching GCOP’s pattern — no clutter build-up at low zoom.
  • Click routing: the Mapbox layer nwfc_observations-click is a zero-opacity circle (radius 18 px) that serves as the popup click target. Marker clicks re-fire a map.fire("click", …) at the feature’s lng/lat which the existing NWFC popup dispatcher in layer-attribute-popup.js catches unchanged.
  • The full string-→bucket catalogue is documented in nwfc_weather_types.txt at repo root.

Weather Report Panel #

The Weather Report is a two-tab panel that renders a dynamic situational summary of everything currently on the map. The default Overview tab handles temporal Meteoblue layers and station networks. The new PMD Overview tab is a dedicated console for the PMD / FFD / NWFC ecosystem.

Overview tab — render pipeline

  1. Read getCurrentTemporalState() for the active layer key + step.
  2. Verify District Boundary & Provincial Boundary layers are toggled on.
  3. queryRenderedFeatures on the district fill layer in the viewport.
  4. Sample the temporal frame at each district’s centroid (or compute station readings via bbox containment).
  5. Group rows by province; compute kind-aware aggregates (mean for most; max for CAPE / helicity).
  6. Render summary stats, hotspot card, threshold pill, and per-province cards with click-to-fly bbox attributes.

Split Compare View #

The Split Compare View (columns-icon on the right rail, #splitCompareToggle) turns the map into a side-by-side dual-map comparison: a full second Mapbox instance is spun up in a right-hand overlay pane, cameras are synced in real time, and a second temporal slider mirrors the first. Everything is additive — no core module was modified.

What activates when you toggle it

  • A new <div class="split-compare-overlay"> is appended over #map, containing an inner pane clipped via clip-path: inset() and a draggable vertical divider.
  • A second mapboxgl.Map is instantiated in the inner pane using the plain mapbox://styles/mapbox/streets-v12 URL (using the primary map’s serialised style caused silent tile-fetch failures on styles with token-scoped sprites — the plain URL always resolves).

  • Map A’s primary slider is repositioned to the top-left half; a full replica #temp-slider2 is built for the top-right half with a MAP B purple badge.
  • A bottom-centre Compare Layer (Map B) picker panel appears, populated by the sidebar catalogue.
  • The right rail + every rail-panel + the NCOP header are hidden via body.split-compare-active scoped CSS. The hamburger menu (#menuToggle) stays visible so Map A layers remain reachable.

Camera synchronisation

The primary map’s move event schedules a requestAnimationFrame-throttled sync onto Map B via easeTo({ center, zoom, bearing, pitch, duration: 0, animate: false }). Pipeline — per-step convert

All backend code lives in ncop_internal/views.py (search for _MON_PRED_ELEMENTS). One endpoint: GET /api/pmd/monitor/predictions/<element_key>/ returning {element, label, unit, run, steps: [{date, url, coordinates, bounds}, …]}.

  2. Discover run — GET /api/modelTimeList?data_type=<model>&element=<code>, take newest. Cached 30 min.
  3. List frames — GET /api/model?date_time=<run>…. Cached 3 h.
  4. Thin steps — hourly through +48 h then 6-hourly to end-of-run, caps texture count per layer at ~20-30.
  5. Per-step convert (parallelized) — ThreadPoolExecutor(max_workers=5): fetch raw .tif, gdal.Warp(dstSRS="EPSG:3857"), gdal.DEMProcessing("color-relief"), write PNG + JSON metadata sidecar under MEDIA_ROOT/pmd_predictions/. Deterministic filename keyed by element_key so future WRFPRS/CAPE + GDFS/CAPE entries can coexist without collision. GDAL PAM_ENABLED=NO scoped per-call, cleanup of intermediates in finally.

Element registry — single source of truth

Each entry in _MON_PRED_ELEMENTS carries data_type, element, label, unit, stops, and optional bbox. The ramp emitter treats stops[0][0] > 0 as “additive quantity” (precip, snowfall) and emits an extra 0 → transparent line so no-signal backgrounds stay clear of the map; for state quantities (temperature, cloud cover, humidity) whose stops start at 0 or below, that synthetic line is skipped.

GDFS bbox clipping — the GDFS feed is a global grid (2847×2846 pixels warped to Mercator = ~32 MB per frame × 48 frames = 1.5 GB of GPU texture per layer, unusable in a browser). Registry entries for cloud-cover and humidity carry bbox: (55, 20, 80, 40) covering Pakistan + neighbours; gdal.Warp(outputBounds=…, outputBoundsSRS="EPSG:4326") clips + reprojects in one pass, dropping the PNG to ~242×226 pixels / ~36 KB per frame (100× smaller). WRFPRS layers are Pakistan-native and omit bbox.

Backend Deep-Dive (Workflows) #

The NCOP backend is a single Django application (ncop_internal) whose entire job is to be a disciplined middleman between a diverse zoo of upstream services and one uniform browser API. It doesn’t author data; it fetches, normalises, caches, colorizes, joins, and re-exposes.

1 · The Zeitgeist — what problems the backend solves

Five recurring problems appear in every “fuse a bunch of external data feeds into one dashboard” project. NCOP’s architecture is organised around solving all five in one coherent set of primitives:

ProblemWhy it mattersNCOP’s answer
Credential leakageAPI keys / JWTs in the browser bundle are permanently compromised.Every credential-bearing call proxied through Django; browser sees only window.location.origin.
Rate-limit thrashFree-tier upstreams throttle at the source IP; N users → 1 / N budget each.Server-side caching (5 min → 24 h) makes N users cost 1 upstream request.
Format zooEvery upstream returns a different shape (JSON, XML, WMS tiles, raw GeoTIFF, HTML scrape).Every Django endpoint returns a normalised JSON that matches what Mapbox directly consumes.
Auth expiryJWTs expire; sessions get invalidated server-side.Retry-once-after-401 pattern — a transient token expiry never surfaces to the user.
Upstream outageOne flaky source shouldn’t break the whole map.Cache-with-stale-fallback wrapper: transient failure serves last-known-good instead of a 502.

8 · Extending the backend — add a new authenticated source in 5 files

Because every source follows the same 5-primitive shape, adding a new one is mechanical:

  1. settings/base.py — add three env-var reads for the new source’s URL / user / pass.
  2. views.py — copy an existing _mon_* block, rename to _newsource_*. Fill in the login body shape.
  3. views.py — write one NewSourceAPIView(APIView) that composes _newsource_get + _newsource_cached.
  4. urls.py — one line to route the new endpoint.
  5. frontend/map-layers.js — register a new layer entry that points at the new endpoint.

No new patterns are invented; no core files are touched; the shape catches every existing failure mode (auth expiry, upstream outage, format drift) automatically because it’s the same shape as everything else.

Caching Strategy #

  • PMD FFD weather: 5-minute in-memory class cache (rainfall/temperature/wind merger).
  • PMD / FFD / NWFC endpoints (2026-Q3 integration): TTL cache with an in-flight request coalesce — duplicate concurrent calls share the same upstream request instead of stampeding PMD Monitor. The 19 live endpoints are cached at the Python layer in views.py and again on the JS side via the getters in gcop-monitor-integration.js.
  • Heatwave Monitoring: on-disk JSON cache at project/cache/heatwave/ with a TTL janitor.
  • GDACS / USGS / EONET: shorter in-process TTL plus retry/backoff on upstream failure.
  • GEE tiles: URL-based tile cache through GEE itself; Django merely returns the tile-URL template.

The on-disk cache directory is git-ignored (project/cache/) so cached snapshots don’t pollute history.

Upstream Proxies #

Every external feed flows through a Django view for three reasons:

  1. CORS — the browser can’t directly hit most upstream endpoints.
  2. SSL — some PMD endpoints use self-signed certificates; the proxy disables verification server-side only.
  3. Schema — the proxy normalises three product feeds into a single station merge (PMD), or unwraps awkward JSON envelopes (EONET, GDACS).

Google Earth Engine #

NCOP integrates Earth Engine through a curated catalogue (/api/gee/catalog/). The client requests a specific dataset; Django authenticates with Earth Engine using the configured service account, applies the dataset’s visualisation parameters, and returns an XYZ tile-URL template that Mapbox consumes directly.

Temporal GEE layers return an array of frame definitions consumable by the temporal slider.

Troubleshooting #

⚠
Assets don’t load on another machine Check VITE_DEV_SERVER_HOST/VITE_HMR_HOST. They’re embedded into the rendered HTML — the browser tries to fetch JS from that exact host. Add the dev machine’s reachable IP to both, and open port 5173 in Windows Firewall. CORS is wide-open in dev (CORS_ALLOW_ALL_ORIGINS=True) so the typical failure mode is “connection refused” not CORS.
⚠
Layer style resets after switching the basemap This is fixed — LayerStyleConfig persists user overrides into #userOverrides and replays them on every SourceLayerControl.addLayerByKey() call. If you ever see this regress, verify the wrapper is still installed in #hookSourceLayerControl().
✕
PMD station endpoint returns fewer points than expected The view merges three product feeds keyed by station name. Whitespace-different names ("Khairpur " vs "Khairpur") won’t collide but also won’t merge — you’ll see two markers at the same place. Normalise upstream or apply .strip() in the merge.
ℹ
Mapbox token errors Confirm MAPBOX_ACCESS_TOKEN is set in .env; the dashboard view injects it into window.MAPBOX_ACCESS_TOKEN at template render. Restart the Django process after changing the env file.
